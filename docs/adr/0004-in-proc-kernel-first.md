# ADR-0004 · 内核先进程内，IPC 边界用 trait 预留

**状态**：已接受 · **日期**：M0（M3 复评）

## 背景

TSF TIP DLL 被注入到**每一个**需要文本输入的进程。test.md 图 6 建议「拆成多个进程或线程」。两种极端：

- **A. 全在进程内**（线程池）：延迟最低、调试最简单；但每个进程各持一份系统词库、各开一条云端长连接、各写一份用户词库（并发写冲突）。
- **B. 一开始就上独立 host 进程**：资源只占一份、崩溃隔离好；但每次按键都要过 IPC，**打字延迟**这个最难归因的问题从第一天就掺入了管道/序列化变量。

## 决定

**M0–M2 采用 A（进程内 worker 线程），但把边界抽象成 `KernelBackend` trait，M3 再实现 B。**

```rust
pub trait KernelBackend: Send + Sync {
    /// 永不阻塞：投递事件后立即返回
    fn submit(&self, ev: InputEvent);
    /// 非阻塞：取出最新渲染状态（无则 None）
    fn poll_render(&self) -> Option<RenderState>;
}

pub struct LocalBackend { /* crossbeam channel + 线程池 */ }   // M0
pub struct RemoteBackend { /* 命名管道 + 共享内存环 */ }        // M3
```

TSF 层只依赖 `Box<dyn KernelBackend>`，切换实现时**上层零改动**。

## 理由

1. **先让正确性和延迟可测量**。`retype-diag` + 进程内内核可以把「按键→候选」的 P50/P95 打到微秒级并稳定复现；有了这个基线，M3 引入 IPC 后才能立刻看出退化多少。
2. **词库共享内存问题可以后置**：`dict.bin` 设计为 mmap 只读（见 [dict.md](../dict.md)），即使每个进程各映射一次，**物理内存也只有一份**（OS 页缓存共享）。所以「多进程各持一份词库」的实际代价远小于直觉。
3. **用户词库并发写**在 M2 之前不是问题：MVP 阶段用户词库写入极少，先用「单写者 + 文件锁 + 后写覆盖」的保守策略，M3 抽 host 时自然变成单写者。

## 代价与触发条件

进程内方案在以下情况必须升级为 host 进程（M3 的验收条件之一）：

| 触发条件 | 原因 |
|---|---|
| 云端长连接 | 每个进程一条 WS 连接不可接受（连接数、鉴权、心跳） |
| 语音音频采集 | 麦克风设备句柄不宜分散在多个进程 |
| 用户词库写冲突 | 多进程同时学习会互相覆盖 |
| 模型/热词缓存 | 需要跨进程共享才有意义 |

## 复评

M3 结束时决定 `RemoteBackend` 是「全量迁移」还是「混合」（拼音首刷留在进程内保证零延迟，只有二刷/语音/学习走 host）。目前倾向**混合**：首刷路径越短越好，这正好符合 test.md「本地保证速度、云端提升准确」的分工。
